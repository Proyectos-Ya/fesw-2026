# 1.1 Ingesta y Perfilamiento — onboarding automático por RUT

Entregable de [#156](https://github.com/Proyectos-Ya/fesw-2026/issues/156).

**Pregunta:** ¿existe una API oficial para consultar una empresa por su RUT, o
hay que caer en OCR del E-RUT? Y si existe: ¿sus actividades económicas sirven
para inferir el rubro y las palabras clave del perfil, o solo para
autocompletar el nombre?

**Respuesta corta:** existen varias APIs oficiales y **funcionan** —cuatro
probadas, tres de ellas a fondo—, y sí sirven para más que el nombre: con el
mecanismo construido en este documento, las actividades económicas producen
`sectors`, `keywords` y hasta la vigencia. **No hizo falta OCR** para nada de
esto — el E-RUT nunca se llegó a necesitar. El OCR del spike quedó por
completo del lado de [#157](https://github.com/Proyectos-Ya/fesw-2026/issues/157)
(validación de documentos administrativos: fechas de vigencia de certificados,
derivar qué documentos exige una base), no de este documento — ver
[`1.2-ocr-alternativas.md`](1.2-ocr-alternativas.md).

Este documento tiene tres partes: **Mapeo de Perfil** (qué API usar y qué
entrega cada una), **Actividades económicas → rubro y palabras clave** (el
procedimiento que se va a usar) y una **prueba pendiente** con RUTs reales.

---

## Mapeo de Perfil

### Inventario de fuentes

Las alternativas que se decidió probar a fondo son **Mercado Público
(BuscarProveedor), Web Empresario, ruts.info y SRE**. Las demás candidatas del
plan original (SII vía web, Registro de Empresas y Sociedades, proveedores de
datos comerciales de pago) quedan **fuera de este spike**: no aportarían más
que las cuatro elegidas para lo que se necesita (identidad, vigencia, rubro,
keywords), y dos de ellas exigían scraping o tenían costo por consulta.

| Fuente | Estado | Resultado |
|---|---|---|
| **Mercado Público — `BuscarProveedor`** | ✅ probada | Identidad únicamente: 2 de 10 campos del perfil |
| **Web Empresario** | ✅ probada | 5 de 10 campos + vigencia + actividades económicas |
| **ruts.info** | ✅ probada | Mismo tipo de dato que Web Empresario, esquema distinto (inglés) |
| **SRE** | ✅ probada **en vivo** | Actividades sin glosa (resuelto con catálogo local); sin domicilio ni vigencia; trae `dte_email`/`es_mipyme` |
| Mercado Público — ficha de empresa | ❌ probada, no existe | `FichaEmpresa` y variantes → 404 |
| Mercado Público — API Compra Ágil v2 | ❌ probada | Solo dos endpoints, ninguno de empresas |
| SimpleAPI | Probada| Queda afuera por temas de tiempo de respuesta |
### Fuente 1 — Mercado Público: `BuscarProveedor`

```
GET https://api.mercadopublico.cl/servicios/v1/Publico/Empresas/BuscarProveedor
    ?rutempresaproveedor=76.086.428-5
    &ticket=<TICKET>
```

```json
{
  "Cantidad": 1,
  "FechaCreacion": "2026-08-25T05:39:35Z",
  "listaEmpresas": [
    { "CodigoEmpresa": "1148259", "NombreEmpresa": "MGM Auditores Consultores Ltda" }
  ]
}
```

Usa **el mismo ticket** que ya tiene el proyecto. No requiere credencial
adicional. Es la fuente más pobre de las cuatro, pero fue la primera en
confirmarse y sigue sirviendo como línea base de comparación.

**Tres detalles que cuesta descubrir:**

1. **El RUT va con puntos.** `76.086.428-5` da 200; sin puntos o sin guion da
   `500 "No hay resultados de empresas."` — el mismo error que "empresa
   inexistente", así que un formato equivocado se confunde con un RUT no
   registrado. Normalizar **a puntos** antes de consultar.
2. **El parámetro se llama `rutempresaproveedor`.** No está documentado en
   ninguna guía del equipo; se encontró probando (`400 "Nombre de parametro
   no válido"` para los nombres incorrectos).
3. **Es búsqueda por coincidencia parcial, no consulta exacta.** Enviar `1`
   devuelve tres empresas. Con un RUT completo devolvió `Cantidad: 1`, pero
   **el contrato no lo garantiza**.

> **Limitación con consecuencias:** la respuesta **no incluye el RUT**. Se
> envía un RUT y se recibe un nombre, sin forma de verificar que corresponden.
> Mitigación mínima: exigir `Cantidad == 1` y tratar cualquier otro caso como
> no concluyente.

**Mapeo al perfil** (`Supplier` en `app/domain/entities/supplier.py`):

| Campo | ¿Lo cubre? | De dónde |
|---|---|---|
| `rut` | ✅ | es la entrada; ya se valida con `is_valid_rut` |
| `legal_name` | ✅ | `NombreEmpresa` |
| `trade_name` · `description` · `regions` · `sectors` · `certifications` · `keywords` · `years_experience` · `num_employees` | ❌ | ninguno de estos |

**Cubre 2 de 10 campos, y ninguno de los que alimentan el matching. Ni
vigencia.** Donde sí aporta valor real: **autocompletar la razón social** al
escribir el RUT, y **confirmar que la empresa existe** como proveedor del
Estado — si no aparece, es señal de que el usuario aún no está inscrito en
ChileProveedores. Las otras tres fuentes resuelven el resto.

### Fuente 2 — Web Empresario

Implementado en
[`poc/perfilamiento/web_empresario.py`](poc/perfilamiento/web_empresario.py) —
**sin llamadas de red**: el módulo interpreta una respuesta ya obtenida.

> **Nota sobre el nombre:** este payload se atribuyó primero a ruts.info por un
> error de etiquetado al copiarlo. Es de **Web Empresario**. El esquema real de
> ruts.info es distinto (Fuente 3, más abajo).

**Cobertura del perfil: 5 de 10 campos (contra 2 de `BuscarProveedor`):**

| Campo | ¿Lo cubre? | De dónde |
|---|---|---|
| `rut` | ✅ | `RUT` + `DV`, validado con `is_valid_rut` del dominio |
| `legal_name` | ✅ | `RAZON_SOCIAL` |
| `regions` | ✅ | `domicilios[].REGION`, normalizado con `normalize_region_name` |
| `sectors` | ✅ | ver "Actividades económicas" más abajo |
| `keywords` | ✅ | ver "Actividades económicas" más abajo |
| `trade_name` · `description` · `certifications` · `years_experience` · `num_employees` | ❌ | siguen siendo del wizard |

**Y además entrega la vigencia**, que era la pregunta que este documento dejó
abierta la primera vez: `FECHA_TG_VIG` vacío significa que no hay término de
giro registrado. Mercado Público no da este dato.

**Tres trampas del formato**, encontradas al escribir el adaptador:

1. **El cero a la izquierda se pierde.** El código de actividad llega como
   **entero**, así que `011101` se recibe como `11101`. Sin reponerlo, se lee
   mal la agrupación del código — un resultado bien formado y equivocado, que
   nadie revisa.
2. **La codificación viene rota.** `CIUDAD` llega como `"VALPARAÃ\x8dSO"`:
   UTF-8 interpretado como Latin-1 en el origen. Reparable, pero solo si el
   carácter de control invisible sobrevive — al pegar el JSON en un editor
   suele perderse.
3. **Los domicilios vienen duplicados**, casi idénticos y con distinta fecha
   de vigencia. Interesa la región, no la dirección, así que se deduplica.

### Fuente 3 — ruts.info

Esquema completamente distinto — campos en inglés, plano, sin el envoltorio
`{success, data}` de Web Empresario:

```json
{
  "code": 77073851, "verification_digit": "2",
  "business_name": "STARLINK CHILE SPA",
  "valid_from_date": "26-09-2019", "valid_until_date": null,
  "activities": [{"activity_code": "619090",
                   "activity_description": "OTRAS ACTIVIDADES DE TELECOMUNICACIONES N.C.P.",
                   "iva_affects": true}],
  "addresses": [{"region": "XIII REGION METROPOLITANA",
                  "district": "LAS CONDES", "city": "SANTIAGO"}]
}
```

Implementado en
[`poc/perfilamiento/ruts_info.py`](poc/perfilamiento/ruts_info.py). Converge al
mismo `PerfilSugerido` que Web Empresario: la lógica de actividades,
normalización de región y armado de avisos se factorizó a
[`poc/perfilamiento/perfil.py`](poc/perfilamiento/perfil.py) para no
duplicarla entre fuentes — agregar una nueva API es escribir un adaptador más,
no repetir el pipeline completo.

**La trampa que esta fuente agrega, y que Web Empresario no tiene:** la
vigencia se expresa **al revés**. Web Empresario usa string vacío
(`FECHA_TG_VIG: ""`) para "sin término de giro, o sea vigente". ruts.info usa
**`null`** para lo mismo (`valid_until_date: null`). Tratar `null` como "dato
ausente" habría marcado como indeterminada a toda empresa vigente — el error
opuesto al que hay que evitar, y silencioso porque el caso más común (empresa
vigente) es justo el que se malinterpreta.

**Pendiente de verificar con más muestras:** en el único ejemplo, `district`
(`"LAS CONDES"`) tiene forma de comuna, y así se está tratando. No hay
confirmación de que sea siempre así.

### Fuente 4 — SRE (probada en vivo)

`sre.cl/api/company_info`. A diferencia de las otras dos APIs de terceros, se
probó **en vivo**: POST con token en el cuerpo, no en la URL ni en una
cabecera — `{"token": "...", "rut": "76668304-5", "version": "2.0"}`.
Respuesta real, confirmada el 26-08-2026:

```json
{
  "razon_social": "Planeta Libre Soluciones Sustentables Limitada",
  "rut": "76668304-5",
  "dte_email": "cl.empresas@defontanadte.com",
  "fecha_resol": "22-08-2014", "numero_resol": 80,
  "actecos": ["433000", "479100", "952200"],
  "url": "", "actualizado": "2026-08-25",
  "glosa_giro": null, "es_mipyme": false,
  "consultas_restantes": 48
}
```

Implementado en [`poc/perfilamiento/sre.py`](poc/perfilamiento/sre.py). Es la
fuente **más pobre de las cuatro para el perfil**, y trae dos datos que
ninguna otra tiene.

**Lo que le falta, y cómo se resolvió:**

- **`actecos` es una lista de códigos pelados — sin glosa.** Se resuelve con
  el propio catálogo del SII ya procesado para este spike
  ([`catalogo_glosas.py`](poc/perfilamiento/catalogo_glosas.py)): la glosa no
  se inventa ni se le pide a otra API, se recupera de una fuente que ya se
  tenía y ya se había verificado. Con eso, SRE produce exactamente los mismos
  `sectors`/`keywords` que Web Empresario para esta empresa.
- **Cero domicilio.** Ni región, ni comuna, ni dirección. SRE no puede aportar
  nada a `Supplier.regions`.
- **Ninguna señal de vigencia.** Sin equivalente a `FECHA_TG_VIG` ni a
  `valid_until_date`.

**Lo que trae de más**, sin campo equivalente en `Supplier` hoy:

- **`dte_email`** — correo de facturación electrónica verificado. Candidato a
  dato de contacto si el producto llega a necesitarlo.
- **`es_mipyme`** — clasificación oficial MIPYME. Hay licitaciones con
  criterios preferentes para MIPYME; podría ser un filtro o una señal de
  segmentación a futuro.
- **`consultas_restantes`** — la API expone su propia cuota en cada respuesta
  (48 en la prueba). Hay que saber el límite del plan antes de usarla en un
  onboarding con volumen.

`fecha_resol`/`numero_resol` se guarda como `fecha_inicio`, pero **no está
claro qué acto administrativo representa** — podría no ser la fecha de inicio
de actividades. No se afirma más de lo que se sabe con un solo ejemplo.

### Comparación de cobertura, las tres APIs de actividades

Sobre la misma empresa (RUT 76.668.304-5, las tres consultadas o interpretadas
el mismo día):

| Campo de `Supplier` | Web Empresario | ruts.info | SRE |
|---|---|---|---|
| `rut` | ✅ | ✅ | ✅ |
| `legal_name` | ✅ | ✅ | ✅ |
| `regions` | ✅ (con domicilios) | ✅ (con `addresses`) | ❌ sin domicilio |
| `sectors` | ✅ | ✅ | ✅ (glosa vía catálogo local) |
| `keywords` | ✅ | ✅ (pobre si la glosa es genérica) | ✅ (glosa vía catálogo local) |
| vigencia | ✅ `FECHA_TG_VIG` | ✅ `valid_until_date` | ❌ ningún campo |
| actividad principal | ❌ | ❌ | ❌ |
| dato extra sin campo propio | — | — | `dte_email`, `es_mipyme` |

**Ninguna de las tres marca actividad principal.** Sigue siendo la pregunta
abierta más importante para desambiguar una empresa con rubros dispares — sin
eso, las tres fuentes producen el mismo aviso de "confirmar con el usuario"
para el ejemplo de esta empresa.

**SRE solo tiene sentido combinada con el catálogo local.** Sola, sin el
respaldo de glosas, cubre menos que las otras dos (nada de región, nada de
vigencia). Con el catálogo, empata en `sectors`/`keywords`.

## Actividades económicas → rubro y palabras clave

### Por qué esto importa: dos hechos del código

Verificados antes de diseñar nada.

**1. Hoy, un perfil sin sectores matchea por el nombre de la empresa.**
[`text_builder.py:42`](../../monorepo/backend/app/application/services/text_builder.py):

```python
if supplier.sectors:
    sections.append(", ".join(supplier.sectors))
else:
    sections.append(supplier.legal_name)   # ← el fallback
```

`sectors` va **primero** en el texto que se embebe. Sin él, el proveedor se
representa por su razón social — "Comercial Los Andes SpA" no dice nada sobre
qué vende. La línea base contra la que se compite es muy baja.

**2. No hace falta una tabla de equivalencias a UNSPSC.**
[`text_builder.py:22`](../../monorepo/backend/app/application/services/text_builder.py)
arma el texto de la licitación con **nombres de ítems en texto libre**, no con
el `codigo_unspsc` (que sí se ingesta pero no entra al embedding). La glosa de
la actividad económica, también texto libre, cae en el mismo espacio
vectorial — no hay que construir ni mantener un crosswalk actividad SII →
rubro UNSPSC, que era el camino caro y frágil.

> Ojo con la tentación de "aprovechar" el `codigo_unspsc` porque está ahí.
> Meterlo al embedding es un cambio al **lado de la licitación**, afecta a
> todos los proveedores y no es parte de este spike.

### El problema real: dos vocabularios distintos

La glosa del SII es lenguaje **tributario**. Las bases usan lenguaje de
**compra**. No siempre se parecen:

| Glosa SII (lo que entrega la API) | Cómo lo escribe una base |
|---|---|
| `620100` Actividades de programación informática | "Desarrollo de plataforma web", "servicio de mantención de sistema" |
| `433000` Terminación y acabado de edificios | "Habilitación de oficinas", "pintura de dependencias" |
| `478000` Venta al por menor en puestos de venta y mercados | — (casi no aparece en compras públicas) |
| `829900` Otras actividades de servicio de apoyo a empresas n.c.p. | nada: es un cajón de sastre |

Las dos últimas filas son la advertencia: una parte del catálogo del SII es
**administrativa**, no descriptiva. Pegarla cruda al perfil puede no aportar y,
en el caso de los cajones de sastre, **acercar la empresa a licitaciones que no
tienen nada que ver**. Ese daño no se ve en una demo; se ve como ruido en el
top-10 de todos los usuarios.

### El procedimiento principal

**Idea central:** a partir de los códigos de actividad que entrega el SII (vía
cualquiera de las tres fuentes de arriba), producir una **lista tentativa de
rubros** —que coincide con el vocabulario cerrado de 19 rubros del wizard— y
una **lista de palabras clave** relacionadas con lo que la empresa hace. Ambas
listas son un punto de partida sugerido, no el perfil final: el usuario las
confirma o corrige en el wizard.

Implementado en
[`poc/perfilamiento/diccionario.py`](poc/perfilamiento/diccionario.py), con dos
niveles de calidad por código, en orden:

**Nivel 1 — Curado a mano** (`CATALOGO` en `diccionario.py`). Un puñado de
códigos verificados contra payloads reales, con rubros y términos de compra
redactados directamente por una persona. Es el mejor resultado posible, pero
no escala a las ~670 actividades del catálogo.

**Nivel 2 — Clasificador por palabras clave, sobre la actividad puntual, no
sobre su sección.** Para cualquier código sin curar:

- **Rubro**: [`clasificador_rubro.py`](poc/perfilamiento/clasificador_rubro.py)
  busca términos como "reparación", "construcción", "consultoría" en el texto
  de *esa* actividad específica, y de ahí intuye a cuál de los 19 rubros del
  wizard corresponde. Se probó primero agrupar por **sección** del SII (21
  categorías), pero resultó demasiado grueso: una sola sección de "comercio"
  mete 105 códigos reales sin relación entre sí (desde maquinaria hasta
  motocicletas) en el mismo rubro. Mirar la glosa puntual es más preciso,
  aunque cueste algo de cobertura: **454 de 674 códigos reales (67%)**
  obtienen un rubro por esta vía, contra 92% agrupando por sección. Una glosa
  sin ninguna palabra reconocida **no fuerza un rubro** — queda sin uno,
  preferible a inventar uno solo por rellenar.
- **Palabras clave**: **solo del Nivel 1** (curadas a mano). A propósito **no
  hay respaldo con la glosa oficial** del SII para `keywords` — se probó, y es
  lenguaje tributario, no de compra (el problema de los dos vocabularios de
  arriba), así que se decidió no aportar ninguna palabra clave antes que
  aportar una que describe mal. Un código sin curación fina simplemente no
  suma palabras clave, y se avisa explícitamente
  (`"sin ninguna palabra clave que coincida"`) en vez de dejarlo pasar en
  silencio. La glosa oficial **sí** se sigue usando para el rubro (punto
  anterior) — la decisión es solo sobre `keywords`.

**Un tercer eje, además de rubro y palabras clave:** el **dominio común**
entre las actividades de una empresa —qué tienen en común, no qué rubro es
cada una—, calculado por intersección. Ejemplo real: una empresa que declara
terminación de edificios, venta por internet y reparación de electrodomésticos
no comparte *operación* entre esas tres actividades, pero sí comparte
*objeto*: las tres trabajan sobre el **hogar**. Esto no se guarda en
`Supplier` (no hay campo para ello), pero es información que puede servir para
redactar una `description` sugerida más adelante.

**Dos errores reales, encontrados y corregidos al construir el clasificador**
(ambos verificados contra el catálogo real, no supuestos):

- La raíz de palabra "ELECTRIC" hacía que "venta al por menor de aparatos
  eléctricos" (un retail) cayera en el rubro "Energía y Electricidad". Se
  corrigió exigiendo frases completas ("energía eléctrica", "instalaciones
  eléctricas") en vez de la raíz sola.
- La palabra "PESCA" hacía que "venta de artículos de caza y pesca" (venta de
  equipo) cayera en "Alimentación y Gastronomía". Se corrigió con una
  excepción puntual para ese caso.

**Cuando una empresa declara varios rubros sin relación entre sí** (el
ejemplo del hogar de arriba: obras + retail + servicio técnico), **el
borrador reporta todos y avisa**, en vez de elegir uno — elegir sería
inventar una precisión que el dato no tiene, y quien sabe cuál aplica es el
usuario. Por la misma razón, un proveedor cuyas actividades son **todas**
genéricas se marca explícitamente: la fuente no aporta nada al matching para
esa empresa.

**Iteración futura, no implementada todavía:** expandir semánticamente la
glosa de cada código del catálogo (~1.000, corrido una sola vez, no por
usuario) para acercarla al lenguaje de compra — reutilizando el cliente de
Gemini que ya existe
([`gemini_deep_analysis_service.py`](../../monorepo/backend/app/infrastructure/services/gemini_deep_analysis_service.py)).
Sería una tabla estática y auditable, no una llamada en caliente. Se deja
para después de medir si el Nivel 2 ya alcanza.

### Esto no reemplaza el wizard

Las actividades económicas son un **punto de partida sugerido y editable**,
nunca el perfil final. Tres razones: pueden estar desactualizadas, una empresa
con ocho actividades registradas genera más ruido que señal, y el usuario sabe
de su negocio más que su carátula tributaria.

Y una oportunidad concreta: si el usuario **corrige** lo sugerido, esa
corrección es el mejor dato que vamos a tener para mejorar el mapeo. Conviene
guardarla desde el primer día, aunque todavía no se use.

### Cómo se va a validar esto contra el matching real (más adelante)

La comparación es entre **cuatro perfiles del mismo proveedor**, contra el
mismo índice de licitaciones:

| Variante | Qué va en el perfil |
|---|---|
| **A — línea base** | solo `legal_name` (lo que pasa hoy con un perfil vacío) |
| **B — glosa cruda** | glosas sin procesar como `keywords` |
| **C — procedimiento actual** | rubro + keywords del Nivel 1/2 de arriba |
| **D — glosa expandida** | si se implementa la iteración futura |

**Procedimiento:** para K empresas reales, consultar sus actividades, armar
las cuatro variantes, correr el ranking que ya existe (`RankTendersUseCase`
sobre el índice de Qdrant) y juzgar **a mano** el top-10 de cada una: ¿le
sirve esta licitación a esta empresa, sí o no? Con K=5 son 200 juicios — una
tarde. Quien juzga no debe saber qué variante produjo cada lista.

**Criterios de corte:** si B no le gana claramente a A, las actividades no
sirven para matching y quedan como autocompletado del wizard. Si C ≈ D, no se
paga la expansión semántica.

**Un mejor ground truth, si aparece:** las **adjudicaciones históricas por RUT
de proveedor** darían una señal objetiva —predecir rubros y contrastar contra
lo que la empresa realmente ganó— sobre cientos de empresas, no cinco. Vale la
pena averiguar si Mercado Público lo expone por RUT.

## Prueba pendiente con RUTs reales

**Estado: pendiente.** Falta que se entreguen 5-6 RUTs reales para correr el
procedimiento completo (API → actividades → rubro y palabras clave) y revisar
a ojo si el resultado tiene sentido para cada empresa — un chequeo de
plausibilidad más rápido y concreto que el experimento A/B/C/D de arriba, y el
paso previo a decidir si vale la pena correrlo.

Herramienta para esto: [`poc/perfilar_ruts.ipynb`](poc/perfilar_ruts.ipynb), un
notebook que toma un RUT (o una lista), lo pasa por cualquiera de las tres
fuentes y muestra nombre, vigencia, región, rubros y palabras clave detectados,
en una tabla comparativa. Instalación:

```bash
cd spikes/spike-1/poc
.venv/bin/pip install -r requirements-notebook.txt
.venv/bin/python -m ipykernel install --user --name spike-1-perfilamiento
cp .env.example .env   # completar con las credenciales reales; .env no se versiona
```

Después abrir `perfilar_ruts.ipynb` con el kernel `spike-1-perfilamiento`
—desde VS Code, JupyterLab o `jupyter notebook`—: el notebook carga `.env`
solo, no hace falta exportar nada en la terminal.

Es la misma lógica que `perfilar_rut.py` (la CLI ya existente,
`--fuente {web-empresario,ruts-info,sre} --rut ...`) — el notebook solo hace
más cómodo revisar varios RUTs seguidos y comparar.

**Cuando lleguen los RUTs:** reemplazar la lista de ejemplo en la celda
"Varios RUTs seguidos" del notebook, correrla, y volcar la conclusión acá
(¿el rubro sugerido tiene sentido en los 5-6 casos? ¿alguno cae en el
"sin rubro determinado" del 33% que no cubre el clasificador?).
